# Family Tree Web App — PRD

2026-09-22 · @Someone

V1 is a single-user, local-first desktop app for building and exploring a family tree, stored as plain Markdown files compatible with Obsidian; v2 adds self-hosting, multi-user editing rights, and mobile access.

## Overview & goals

A private tool for recording and exploring an extended family tree: who's related to whom, the key facts about each person, and their life story — in a format that outlives the app itself.

**Goals**

- Make it fast to capture a person and their relationships as the tree comes together from memory, conversations, and old records.
- Represent the messiness of real families: multiple marriages, divorce and remarriage, step- and half-relations, unknown dates.
- Store everything as plain Markdown so the data is never locked in — it should open cleanly as an Obsidian vault, with or without this app.
- Give the tree a visual home (desktop canvas) that feels like exploring a mind map, not filling out a database form.

**Non-goals (v1)**

- Multi-user access or editing rights for other family members (v2).
- Mobile use (v2, alongside self-hosting).
- Public hosting or sharing — this is a private family record.

## Scope: v1 vs v2

The deciding architectural fact: the **File System Access API** (the mechanism that lets a browser app read/write a real folder on disk with no backend) only works in desktop Chrome/Edge — not on any mobile browser. That constraint sets the phase boundary cleanly.

|  | v1 | v2 |
| --- | --- | --- |
| Users | You, solo | You + select family members |
| Storage | Local folder, read/write via File System Access API | Self-hosted backend serving the same Markdown data |
| Platform | Desktop (Chrome/Edge) only | Desktop + mobile |
| Editing rights | You only | Shared, with per-person or per-link access |
| Canvas | Endless pan/zoom canvas | Same, tuned for hundreds of people |
| Mobile view | Not available | Outline view (ancestors/descendants) |
| GEDCOM import/export | Out of scope | Candidate |
| Version history | Out of scope (candidate: git-backed vault) | Candidate |
| Conflict handling | N/A (single user) | To be designed — explicitly deferred |

Everything below describes v1 unless marked (v2).

## Data model: the person object

Each person is one Markdown file. Fixed fields live in the frontmatter (the YAML block Obsidian shows as "Properties"); the life story is the file's body text. The schema is fixed for the common fields, but any file can carry extra ad-hoc keys the app doesn't know about yet — it should render them generically rather than dropping them.

**Core fields**

| Field | Type | Notes |
| --- | --- | --- |
| `id` | string | Stable identifier, never shown as the primary label. Suggest a slug (`jiri-novak-1978`) for Obsidian readability, falling back to a short random suffix on collision. |
| `name` | string | Full display name. |
| `gender` | string | Free text or small fixed set — confirm preference when building. |
| `dob` | date, nullable | Supports unknown — see below. |
| `dob_precision` | enum: `exact` \| `approx` \| `unknown` | Needed because spouse ordering and age display depend on this. |
| `birthplace` | string |  |
| `dod` | date, nullable | Death date. |
| `deathplace` | string |  |
| `occupation` | string |  |
| `photo` | relative path | See Person detail section. |
| `parents` | array | See Relationships section — mirrored, not hand-edited. |
| `children` | array | Mirrored. |
| `spouses` | array | Mirrored. |

**Extensibility**: any additional frontmatter key on a person file is preserved and displayed (e.g. as a generic "details" list) even though the app doesn't have a dedicated field or editor for it yet. This lets you jot down new attribute types as they come up without a schema migration; promoting a common ad-hoc field into a first-class one with its own editor is a v2-style incremental change, not a rewrite.

**Identity**: `id` is generated once at creation and never changes, even if the person is renamed — this is what relationships reference, so renames can't silently break links.

## Data model: relationships

**Storage design.** Two competing requirements came up: a separate relationships file is the more pragmatic source of truth (no dual-write bugs), but relationships should also be bidirectional so the person files stay readable in Obsidian. Resolution: a **relationships index file is the source of truth**; the app **auto-mirrors** the relevant links onto each person's frontmatter (`parents`, `children`, `spouses`) purely for readability. Mirrored fields are regenerated by the app on every change and are never hand-edited — editing a person file's relationship fields directly in Obsidian will be overwritten on next app save. Flag if you'd rather they be hand-editable and reconciled instead.

**Relationship types**

| Type | Direction | Notes |
| --- | --- | --- |
| Parent / child | Biological, step, or adoptive | Recorded once per link; both `parents` and `children` mirrors update together. |
| Sibling | Derived, not stored | Computed from shared parent links — full (both parents shared), half (one shared), step (no shared biological parent, linked only via a parent's spouse). |
| Spouse / partner | Ordered, with status | See below. |

**Spouse/partner entries** — one entry per relationship period, not one per person, so divorce-and-remarriage-to-the-same-person is representable:

```
spouses:
  - partner_id: p_0231
    status: married # married | divorced | widowed | partnered
    start_date: 1975-06-14
    start_date_precision: exact # exact | approx | unknown
    end_date: 1989-03-01
    order: 1
```

- `order` is the displayed "1st spouse / 2nd spouse" label. It defaults to chronological by `start_date`, but is a **manual override field** for the common case where a date is unknown or ambiguous — the app should propose an order and let you correct it, never block on a missing date.
- Divorce-then-remarriage to the same partner is two separate entries with the same `partner_id` and different date ranges, not one entry with a gap.
- Step-parent relationships (needed to derive step-siblings) come from a person's parent's spouse entry — no separate step-parent field is needed if spouse data is complete.

**Add/edit flow implication**: because the graph file is the source of truth, every relationship change goes through the app's UI (never direct file edits) so both the index and the mirrors stay in sync. This is the practical trade-off for keeping the Markdown human-readable without becoming two sources of truth.

## File and folder structure

```
FamilyTree/                      ← the Obsidian vault / chosen folder
  people/
    jiri-novak-1978.md          ← frontmatter + life story body
    anna-novakova-1980.md
    ...
  photos/
    jiri-novak-1978.jpg          ← one file per person, referenced by the person's `photo` field
    anna-novakova-1980.jpg
  _index/
    relationships.json           ← app-generated source of truth for relationships; not meant for manual editing
    layout.json                  ← (optional) saved canvas positions, if auto-layout is manually overridden
```

- `people/*.md` are plain Obsidian notes — fully readable/searchable there, with the relationship fields as read-only mirrors.
- `_index/*.json` is regenerated by the app; treat it like a build artifact rather than a document. Keeping it JSON (not Markdown) makes clear it isn't meant for manual editing, and it's what the desktop canvas actually queries for fast rendering rather than re-parsing every person file on load.
- On startup, the app should be able to **rebuild `_index/relationships.json` from the person files' mirrored fields** if the index is ever lost or gets out of sync — this keeps the person files as the ultimate fallback of truth even though the index is the primary source day-to-day.

## Functional requirements

### Add-person flow

Quick-add by default: name + one relationship is enough to create a person; every other field can be filled in later from their detail view. Clicking an existing person's tile opens an **Add menu** with three options, each pre-filling the new relationship:

- **Add child** — creates the new person as a child of the clicked person (and of their current spouse, if one is selected/obvious).
- **Add partner** — creates the new person and opens the spouse/partner fields (status, start date) inline.
- **Add parent** — for backfilling an unmapped parent, e.g. when a spouse was added without their own parents on the tree yet.

A general "+ new person" action (not tied to an existing tile) is also needed for starting a tree from scratch or adding an unconnected branch.

### Desktop canvas

An endless, pan/zoom canvas in the style of Miro or MindNode — not a rigid genealogy chart. Target scale: a few dozen people in v1, designed to hold up into the hundreds by v2.

- **Layout**: auto-arranged by generation (rows), with couples grouped side by side and a connector to their children below. Needs to handle a person appearing once but connecting to multiple spouses/family units (from remarriage) without the diagram becoming unreadable.
- **Manual override**: drag-to-reposition should be supported and persisted (`_index/layout.json`), since auto-layout won't get every blended-family case right.
- **Interaction**: click a tile to open the Add menu or jump to that person's detail view; the canvas is the primary navigation surface.

### Person detail: life story & image

- **Life story**: free-form Markdown, stored as the body of the person's file (below the frontmatter) — no imposed structure, so it reads naturally in Obsidian too.
- **Image**: one photo per person in v1 (gallery support deferred). Stored in `photos/`, referenced by relative path in frontmatter. Given the precedent from other projects, a light manual crop step on upload is worth including so photos display consistently on tiles.

## Technical architecture (v1)

Consistent with the single-file, no-build, no-backend pattern used elsewhere:

- **Shell**: a single self-contained HTML file, vanilla JS, no framework, no build step.
- **Storage access**: File System Access API — the user grants folder access once (`showDirectoryPicker()`); the app reads/writes `.md` and `.json` files directly. This is what makes "local folder that's also a real Obsidian vault" possible without a server.
- **Frontmatter parsing**: a small hand-written YAML-frontmatter parser/serializer is enough — the schema is simple and fixed, so a full YAML library is unnecessary weight.
- **Canvas rendering**: plain DOM elements (person tiles as absolutely-positioned divs) inside a single pannable/zoomable container using CSS transforms, rather than `<canvas>` or SVG. At dozens-to-hundreds of nodes this performs fine, and DOM tiles make text, images, and click targets far simpler than drawing them manually.
- **Layout algorithm**: a generation-based layered layout (compute each person's generation via BFS/DFS from any root, position couples together within a generation row, draw connector lines to children) — a known, tractable class of algorithm, not a novel one.
- **No dependencies beyond**: a way to persist manual layout overrides (`_index/layout.json`) and image handling for the crop step.

This keeps v1 at the same complexity level as prior single-HTML-file builds, with the File System Access API as the one new technique to validate early — worth a small spike (folder picker → read → write → re-read) before building the rest, per the usual approach.
