# Gen — Family Tree

A private, local-first tool for building and exploring a family tree. Your
data lives as plain Markdown files in a folder you choose on your own
machine — the same folder opens cleanly as an [Obsidian](https://obsidian.md)
vault, with or without this app.

See [`docs/PRD.md`](docs/PRD.md) for the full product spec.

## Running it

This is a single self-contained HTML file — no build step, no install, no
backend.

The File System Access API (`showDirectoryPicker`) that lets the app read
and write your chosen folder requires a *secure context*, which Chrome
does not consider a bare `file://` page to be. Serve the file locally
instead:

```
npx serve .
# or: python3 -m http.server 8000
```

Then open the printed URL in **desktop Chrome or Edge** and click
**Open folder…**, choosing (or creating) an empty folder for your tree.

It's also deployed to GitHub Pages on every push:
https://jiri-studioprobe.github.io/gen/

### Trying it without a real folder

The File System Access API is Chromium-desktop only — it doesn't exist on
iOS/iPadOS in *any* browser (Safari, Chrome, Arc — they're all WebKit
under the hood there, by Apple's rules), and Firefox/Safari on desktop
don't implement it either. On any of those, **Open folder…** is disabled
and you'll see an explanation.

Click **Try demo** instead: it loads a small sample family tree entirely
in memory, so you can try the canvas, Add menu, drag-to-reposition, and
detail panel from a phone, tablet, or any browser. Nothing is saved —
there's a banner reminding you of that, and refreshing resets it. Useful
for UI work; switch to a real folder on desktop Chrome/Edge once you need
persistence.

## How your data is stored

```
YourFolder/
  people/
    jiri-novak-1978.md      ← frontmatter (facts) + free-form life story body
  photos/
    jiri-novak-1978.jpg     ← one photo per person, cropped on upload
  _index/
    relationships.json      ← source of truth for who's related to whom
    layout.json              ← saved canvas positions, if you've dragged tiles
```

- `people/*.md` files are plain Obsidian notes — searchable and readable
  there directly, including in Obsidian's Properties panel.
- The `parents` / `children` / `spouses` fields on each person file are
  **mirrors**, regenerated by the app from `_index/relationships.json` on
  every save. Don't hand-edit them in Obsidian — edit relationships through
  the app's Add menu and person detail panel instead, or your edits will be
  overwritten on the next save.
- If `_index/relationships.json` is ever lost, the app rebuilds it
  automatically from the mirrored fields on your person files the next time
  you open the folder.
- Any extra frontmatter key you add by hand to a person file (something the
  app doesn't have a dedicated field for yet) is preserved and shown, not
  dropped.

## Using it

- **+ New person** (top right) starts an unconnected person or a whole new
  tree.
- Click any person's tile to open the **Add menu**: add a child, add a
  partner, add a parent (for backfilling a spouse's own parents), or jump
  to that person's detail view.
- Drag a tile to reposition it manually — the auto layout (grouped by
  generation, couples side by side) won't get every blended family right,
  and manual positions are saved.
- Scroll to zoom, drag empty canvas space to pan.
- The detail panel lets you edit a person's facts, life story (Markdown),
  photo (with a quick crop step), and their spouse/partner history
  (status, dates, and the 1st/2nd/… order — auto-suggested from dates but
  overridable).

## v1 scope

Single-user, desktop Chrome/Edge only, local folder storage. Multi-user
editing, mobile access, GEDCOM import/export, and version history are
deferred to v2 — see the PRD for the full scope table and backlog.

## Development

The whole app is `index.html`: markup, styles, and script in one file, by
design (see the PRD's Technical Architecture section). There's no
framework and no bundler.

Pure logic (the hand-written YAML frontmatter parser, relationship
mirroring, sibling derivation, and the generation-based layout algorithm)
has a zero-dependency regression test that runs the app's own `<script>`
block in a Node `vm` sandbox:

```
node tests/core.test.mjs
```

## Design decisions worth knowing about

A few calls were made without a round-trip back to the PRD's open
questions, on the theory that they're easy to change later and shouldn't
block getting a working v1 in front of you:

- **`gender`** is free text (with a `male` / `female` / `other` suggestion
  list, not enforced) — the PRD leaves this open; free text matches the
  "everything else free text" spirit of the rest of the schema.
- Spouse **`status`** is the one closed vocabulary
  (`married` / `divorced` / `partnered` / `widowed`), as the PRD's own
  example already fixes it.
- GEDCOM import/export is out of scope, as the PRD's scope table already
  states.

Flag any of these if you'd rather they were different — they're isolated
enough to change without touching the storage format.
